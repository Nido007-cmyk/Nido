## 1. REGRESIONES (los fixes rompieron o rompen funcionalidad)

### R1 — HIGH — B3: `manualDisconnectPks` mata reconexiones manuales posteriores
**Archivo:** `src/p2p/nativeTransport.ts:787, 1164-1166`

`disconnect()` agrega el pkHex a `manualDisconnectPks` **incondicionalmente**, incluso cuando no hay ningún handshake en curso. El flag solo se consume en `establishRoute()`. `connect()` nunca lo limpia.

**Secuencia que lo rompe:**
1. Usuario conectado al peer X, toca Desconectar → `manualDisconnectPks.add(pkX)` (stale desde aquí, no hay handshake que matar).
2. Usuario toca Conectar para el peer X (flujo manual normal) → handshake → `establishRoute()` → `manualDisconnectPks.has(pkX)` es TRUE → **rechaza a todos los waiters con "Desconectado por el usuario durante el handshake"** y cierra el socket.

El usuario pidió conectar explícitamente y el fix lo mata. Es el flujo manual principal de P2P.

**Fix recomendado:** solo agregar a `manualDisconnectPks` cuando no se resolvió MAC por `pkToMac` (indicio de handshake en curso); y/o limpiar el flag en `connect()`; y/o registrar timestamp del disconnect y compararlo contra el inicio del handshake en `establishRoute` (solo matar si el disconnect ocurrió *durante* este handshake).

El mismo patrón de staleness existe en `manualDisconnectMacs` (pre-existente, solo se consume en `scheduleReconnect`), pero B3 lo vuelve crítico porque ahora **mata activamente** en vez de solo suprimir auto-reconnect futuro.

### R2 — MEDIUM-HIGH — K5: gate biométrico duro bloquea ver el DEK sin biometría/PIN
**Archivo:** `src/ui/BackupScreen.tsx:48-53`, `src/security/biometricGate.ts:128-147`

`requireUnlock()` lanza `BiometricUnavailable` si el dispositivo no tiene biometría **ni credencial del sistema** configurada. El `catch` en `handleCreateBackup` trata todo igual: "Cancelado / No se mostró la clave" → return.

**Consecuencia:** en un dispositivo sin PIN/patrón (tablets de prueba típicas), el usuario **jamás puede ver su DEK** después de crear el backup. Antes el Alert lo mostraba incondicionalmente. El backup se crea pero la clave es irrecuperable por UI.

**Fix recomendado:** si `BiometricUnavailable`, mostrar advertencia explícita ("tu dispositivo no tiene bloqueo; cualquiera con el teléfono puede ver esta clave") y permitir continuar bajo consentimiento, o usar `ensureUnlocked` con fallback documentado. El gate duro solo tiene sentido cuando *hay* algo que pedir.

### R3 — HIGH — K3: restore de knowledge DB escribe a la ruta equivocada
**Archivo:** `src/security/backup.ts:296`

```ts
const knowledgeDbPath = dbPath.replace(/\.db$/, "_knowledge.db");
// produce: .../SQLite/nido_memory_knowledge.db
```

La knowledge DB viva es `.../SQLite/nido_knowledge.db` (`KNOWLEDGE_DB_NAME`, línea 33; `knowledgePath` línea 84). K3 copia el backup a un archivo huérfano que nada lee; la `nido_knowledge.db` real queda intacta (stale — exactamente el problema que K3 debía resolver) y se deja basura `nido_memory_knowledge.db` en el directorio.

**Agravantes:**
- Sin safety copy/rollback para la knowledge DB (la principal sí tiene `.pre-restore-*`).
- No se cierra ninguna conexión de knowledge DB antes de sobrescribir (la principal hace `closeDatabase()` en el paso 3).

**Fix recomendado:** derivar la ruta de `documentDirectory + SQLite/nido_knowledge.db` (o `dbPath.replace("nido_memory.db", KNOWLEDGE_DB_NAME)`), con safety copy y cierre previo equivalentes a la principal.

## 2. FIXES INCOMPLETOS

### I1 — MEDIUM — B1 incompleto: el singleton UI sigue disparando vía redescubrimiento
**Archivos:** `src/ui/NidoScreen.tsx:321-327, 354`, `src/p2p/reconnectManager.ts:137-155`

B1 eliminó `reconnectManager.schedule()` de `onPeerLost`, pero `notifyPeerLost` / `notifyPeerFound` siguen cableados. El `lostPeers` set **nunca se limpia** cuando el transporte reconecta con éxito (nadie llama `reconnectManager.cancel()`; el transporte no conoce el singleton).

**Secuencia:** peer cae → transporte reconecta OK (loop de transporte) → `lostPeers` conserva el pk → discovery re-encuentra al peer → `notifyPeerFound` → `lostPeers.has` TRUE, `entries` vacío → `schedule()` → `handleConnectPaired` hace un barrido de MACs **estando ya conectado** (no verifica conexión existente antes de `shouldDialPeer`).

No es la tormenta HELLO original (ese requería ambos loops en cada disconnect), pero es churn de radio redundante en un flujo común. La dirección del audit original era "pick ONE owner"; el singleton debió des-cablearse por completo o el transporte debe notificarle el éxito.

### I2 — MEDIUM — F-DELEG-3: el abort es código inalcanzable
**Archivo:** `src/agent/delegation/delegationService.ts:315-326`

El branch `TASK_CANCEL` vive **después** de `if (!tracked) return` en la ruta de tareas *outbound*. Un TASK_CANCEL inbound (el peer cancela la tarea que *nosotros* estamos ejecutando) nunca tiene entrada en `this.outbound` → return temprano → `running.abort()` jamás se ejecuta. `runningExecutors` (inbound) y `outbound` son conjuntos disjuntos por construcción del protocolo.

El issue original ("TASK_CANCEL can't abort a running executor") **sigue abierto**. Sin test que lo cubra (ningún test referencia `abort`/`TASK_CANCEL`).

**Fix recomendado:** manejar TASK_CANCEL inbound *antes* del check de outbound (buscar en `inboundIndex`/`runningExecutors` primero), o duplicar el branch para la dirección inbound.

### I3 — LOW — K1/K2: checks de manifest silenciosamente ausentes en backups SAF
`validateBackup` busca `${uri}.manifest.json`. El flujo "Guardar en Descargas" (SAF, batch #3) no garantiza que el `.manifest.json` acompañe al `.db` si el usuario mueve/copia solo el archivo. En ese caso los checks K1/K2 se omiten sin aviso (graceful, pero la protección que K1/K2 prometen no existe para esos archivos).

### I4 — LOW — K3: la knowledge DB nunca tiene manifest
`createBackup` solo escribe manifest para la DB principal. En el restore K3, `validateBackup(knowledgeBackupUri)` busca `<dest>.knowledge.db.manifest.json`, que no existe → el check SHA (K2) jamás aplica a la knowledge DB.

### I5 — LOW — 5.1: tokens en buffer se pierden si `generate()` lanza
El `flushTokenBuffer()` final está después de `await llamaEngine.generate(...)`, no en `finally`. Si genera lanza, los tokens de los últimos <100 ms no llegan a la UI (el `assistantText` persistido sí está completo; es solo cosmético en ruta de error). El botón Stop sí flushea (el await retorna).
