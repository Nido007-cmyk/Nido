### 1.8 CR-2 (F-KEY-1 UI + startup wiring) — ⚠️ PARTIALLY CORRECT

**Correct:**
- `App.tsx:182-213`: `checkStaleRekeyStaging` called in `runStartupGate` with
  3-arg probe-based signature (stagingPath, storeDek, openDb). Staging path
  `${FS.documentDirectory}rekey-staging.json` matches `rotateDatabaseKey`'s default.
  Failure doesn't block startup (warn + continue). Correct.

**Incorrect / incomplete:**
- **CR2-PATH (CRITICAL, latent):** `src/ui/BackupScreen.tsx:100` hardcodes
  `const dbPath = \`${dbDir}SQLite/nido.db\``. The real database is `nido_memory.db`
  (`src/agent/memory/memoryStore.ts:47`; `MANAGED_DB_NAMES` in secureDatabase.ts:435).
  `SQLite.openDatabaseAsync` **creates the file if missing** → rekey would run
  `PRAGMA rekey` on a fresh empty `nido.db` (trivially succeeds) → new DEK stored
  in keystore → real `nido_memory.db` unopenable with new DEK → **total data loss**.
  Currently unreachable (BackupScreen is never imported — verified by grep),
  but this is a live brick the moment anyone wires the screen up.
- **CR2-MULTIDB (HIGH, latent):** `MANAGED_DB_NAMES = ["nido_memory.db",
  "nido_knowledge.db", "aoair_knowledge.db"]` — all share one DEK. Rekeying only
  one DB leaves the others encrypted with the old DEK → they become unopenable.
  A correct rotation must rekey all three (or document why not).
- **Unreachable UI:** `BackupScreen` has zero importers (only a comment mention in
  App.tsx:212). The "Rotar clave" button exists but no user can reach it. CR-2's
  "UI wired" claim is not true in any reachable sense.

### 1.9 CR-4 (revocation persistence) — ⚠️ PARTIALLY CORRECT

**Correct:**
- `src/p2p/nativeTransport.ts:326-360`: `loadRevokedPks()` / `saveRevokedPks()`
  using `${FS.documentDirectory}revoked-peers.json`. Save called in `revokePeer`
  (`:855`) and `unrevokePeer` (`:865`). Lazy load in `isRevoked` (`:874`) and
  at the `establishRoute` check (`:1247`). No signature breakage (`isRevoked`
  has zero callers, verified).
- Fail-open on load failure is the safe direction for revocation (user can re-revoke).

**Incomplete:**
- `revokePeer` / `unrevokePeer` have **zero callers** outside nativeTransport.ts
  (the `replayProtection.ts:114` `revokePeer` is a different method for handshake
  nonces). No UI entry point exists. Revocation still cannot be triggered by any user.
- The red-team R3 finding ("dead code end-to-end") stands: persistence works, but
  there's nothing to persist because revocation is never invoked.

## 4. Recommendation

**DO NOT SHIP** — not because of regressions (there are none in reachable code),
but because CR-2 was claimed complete and is not:

1. **Fix CR2-PATH:** derive the DB path from the canonical source (not a hardcoded
   string). Use `nido_memory.db` via the same directory logic as `secureDatabase.ts`.
2. **Fix CR2-MULTIDB:** rekey all `MANAGED_DB_NAMES`, or explicitly scope rotation
   to `nido_memory.db` with a documented reason the others don't need it.
3. **Wire or remove:** either make BackupScreen reachable (import it in the settings
   flow) or delete the dead UI. Dead security UI is worse than none — it creates
   the illusion of a working feature.
4. **CR-4 UI:** add a revoke/unrevoke entry point (contact long-press or settings),
   or document unpair as the revocation path and remove the dead mechanism.
5. Then: targeted tests → tsc → full suite → re-audit #9.

The 16KB llama.rn issue draft (`docs/research/LLAMARN_16KB_ISSUE_DRAFT.md`) is
correctly prepared for manual posting. The physical Tab A9+ gate remains the
binding constraint for any public-APK claim.
