### 2.1 PARTIAL-REKEY — analysis

`rotateAllDatabaseKeys` rekeys DBs sequentially with one staged `newDekHex`,
but the staging does **not** include `oldDekHex`, and `checkStaleRekeyStaging`
stores the staged DEK to the keystore if **any** listed DB opens with it.

Failure windows:
1. **Crash (or rekey throw) between DB #1 and DB #2/#3 rekey.** Staging says
   `{newDekHex, dbPaths:[all]}`. Recovery: DB #1 opens with newDek →
   `storeDek(newDekHex)` overwrites the keystore → DBs never rekeyed still
   hold the old DEK, which is now lost → **those DBs are bricked**.
2. **Asymmetry worth noting:** failure on DB #1 is *safe* (no DB opens with
   newDek → "crash antes del rekey", staging deleted, keystore intact). Only
   failure on DB #2 or later bricks.
3. **storeDek-failure revert path:** if one DB's revert `PRAGMA rekey` throws,
   the `catch {}` swallows it and staging is still deleted — recovery can no
   longer help that DB. (Requires double fault: keystore write fails AND a
   revert fails.)

Probability is low (millisecond window between local PRAGMA rekeys, or I/O
faults), consequence is loss of the non-rekeyed DBs (knowledge DBs are
re-downloadable; `nido_memory.db` would be the severe case). The code path is
currently unreachable by any user.

**Prescribed hardening (before BackupScreen is ever wired to navigation):**
stage `oldDekHex` alongside `newDekHex`; make recovery converge **per-DB**
(try newDek → if opens, done; else try oldDek → if opens, rekey to newDek;
else fail closed without touching the keystore); only `storeDek(newDekHex)`
after **all** listed DBs converge; do not delete staging if any revert threw.
