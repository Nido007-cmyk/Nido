What the fix does:
- `runningPeers: Map<string, string>` declared at line 580.

Key-normalization consistency (the classic bug class in this module) — verified:
- `ctx.taskId` is lowercased at creation: line 418 (`taskId: body.taskId.toLowerCase()` in `handleTaskRequest`). The same `ctx` object flows into `inboundIndex` and into `approveTask`, so both `runningExecutors.set` and `runningPeers.set` use the lowercase key.

- Peer comparison: `ctx.peerPkHex` is stored raw from `fromPkHex` (line 419), but every comparison uses `.toLowerCase()` on both sides (lines 293, 301). `senderPk` is `fromPkHex.toLowerCase()` (line 284). Consistent.

Regression originally reported (G4 check dropping legitimate cancels for in-flight tasks): **fixed**. A legitimate cancel for an approved task now hits the `runningPeers` fallback and reaches `running.abort()` (line 313).

### 1.2 H2-RESIDUAL — isAborted() suppression — CORRECT

**Files:** `src/agent/delegation/executor.ts`, `src/agent/delegation/delegationService.ts`

What the fix does:
- `DelegatedExecutor.isAborted()` is public at executor.ts:146–148, returns `this.aborted` (the flag set by `abort()`, line 105/140).
- `approveTask` (delegationService.ts, ~line 496) now checks:
  ```ts
  if ((!result.ok && result.error?.code === "aborted") || executor.isAborted()) {
  ```
  instead of only the error-code check.

Why this was needed (verified against executor.ts):
- `abort()` sets a flag checked only in `checkBudget()` (executor.ts:129–130), which throws `Error("task aborted by peer (TASK_CANCEL)")`. That throw is converted by the `execute()` catch into `{ok:false, error:{code:"aborted"}}` (lines 210–216, verified the `"aborted by peer"` / `"TASK_CANCEL"` substring match at line 213).
- But if the abort lands **during `modelInvoke`** — after `checkBudget()` already ran — `execute()` returns normally (possibly `ok:true`). The old check `result.error?.code === "aborted"` would miss it and TASK_RESULT would be sent. The new `|| executor.isAborted()` closes this residual window: the flag is latched regardless of where the abort landed.
- In the suppression branch, the code audits with `state: "aborted"` and returns `false` without calling `sendFn` — TASK_RESULT is not sent in either abort path.

Correctness notes:
- `executor` is still in scope after the `finally` (declared before `try`), so `executor.isAborted()` is safe.
- No false positives: `isAborted()` is only true if `abort()` was called, which only happens via the TASK_CANCEL handler (F-DELEG-3) after the G4 ownership check. A non-aborted execution can never have the flag set.

### 1.3 K2-TYPEFAIL — manifest type guards — CORRECT

**File:** `src/security/backup.ts`

What the fix does:
- Line 265: `if (typeof manifest.sha256 !== "string" || !manifest.sha256)` → fail-closed **before** the `.toLowerCase()` at line 272. Previously a truthy non-string `sha256` (e.g. a number) would throw in `.toLowerCase()`, the outer `catch` would swallow it, and the SHA check would be silently skipped (fail-open).
- Line 278: `if (typeof manifest.dekFingerprint !== "string")` → fail-closed before `.toLowerCase()` at line 289.
- Cross-checked `validateBundle` (line ~193): already had `typeof m.sha256 !== "string" || typeof m.dekFingerprint !== "string"` guards — no parallel gap there.

Both `.toLowerCase()` call sites on manifest fields in `validateBackup` are now dominated by their type guards. No remaining unguarded string-method calls on manifest-derived values found in `src/security/backup.ts` (grep of all `.toLowerCase()` in the file: lines 272, 289 — both guarded).
